# FastH3 Omni 比較: 新旧各2本の生成を確認

2026-10-21。**参照画像からのFastH3 Omni生成はA100 40GBで成功。音声付きMP4を2本保存し、VMの出力とハッシュ照合済み。**
既定は旧H3を維持し、`--model fasth3-omni` で参照画像の新経路を選べる。
開始・終了フレーム、音声ガイド、ControlNet等への全面置換は対象外。

## 生成時間と出力

同じ画像・プロンプト、seed 1/2、1344×768、24fps、nominal 5秒で比較した。
全4本が124フレーム、映像5.166667秒、音声5.166688秒（AAC / 32kHz / stereo）。

| 計測 | 旧MiniMax-H3 | FastH3 Omni |
| --- | ---: | ---: |
| seed 1 VMジョブ | 469.0秒 | **182.4秒** |
| seed 2 VMジョブ | 242.4秒 | **98.4秒** |
| seed 1 呼び出し〜ハッシュ照合 | 524.253秒 | 244.101秒 |
| seed 2 呼び出し〜ハッシュ照合 | 300.252秒 | 132.093秒 |
| bootstrap（取得等） | 218.3秒 | 610.5秒 |
| 割り当て前の確認〜解除後の確認（2本全体） | 1119.199秒 | 1082.373秒 |
| LUFS-I / true peak、seed 1 | -16.4 / -6.4 dBFS | -19.0 / -9.3 dBFS |
| LUFS-I / true peak、seed 2 | -12.4 / -1.9 dBFS | -22.4 / -12.4 dBFS |
| 黒画面 / 0.6秒以上の静止の検出 | なし | なし |

起動後2本目のVMジョブは約2.46倍速（約59%短縮）。参照の再encode等を含むジョブ全体であり、純粋なdenoise比較ではない。
旧側の初回には追加の参照用重み取得も含まれる。新側は取得制限対策として並列数を抑えた設定で実行し、
今回のbootstrapは長かった。起動・取得・転送・停止を含む全体では今回約3%の差で、少数試行から一般化しない。
途中の進捗バーはモデル初期化後に時間表示が切り替わるため、比較は完了時に記録したジョブ時間を使った。

各8時点のシートでは、両モデルとも黄色い機体・白煙・雲を維持。新側2本は概ね水平な雲の地平線を保ち、機体が旋回する。
機体が小さく、微細なマーキングや形状の完全一致、連続再生のちらつきは未判定。
新側の音量は小さめ。音声トラックと音量は測定したが、**聴感・エンジン音と動きの同期は未評価**。
この実行環境は音声入力に非対応。元動画・音声は補正せず保持した。

## 失敗の原因と修正

1. 初回はHugging Face XetのHTTP 429。並列2ファイル・Xet並列4・限定バックオフに変更した。
   その後の2回は全4ファイルが各1回の呼び出しで取得できた。429の根本原因が並列数だったとは断定しない。
2. 最初の再試行はGPU照会の終了コード6。停止済みVMの根本原因は不明。
   名前・容量をCUDA Driver APIでも確認し、標準出力・エラーを保存する事前検査を追加した。
3. GPUと全重み取得を通過した後、**こちらの互換チェックのバグ**が見つかった。
   固定版ComfyUIのV3 Comboは `["COMBO", {"options": [...]}]` だが、旧V1形式の配列と解釈し、
   Kitchenが存在しても未対応と判定していた。両形式に対応し、FastH3の機能検査を重み取得前へ移した。
   [固定版の変換処理](https://github.com/Comfy-Org/ComfyUI/blob/b1a247c9cf9dbfda4b2c0a0c1d50950667eeaa0c/comfy_api/latest/_io.py#L2082)。

実機の同じノード情報・同じassertionで修正前は失敗、修正後は成功することを再現した。
さらにA100上でKitchen INT8 attentionを直接実行し、有限値の出力を確認した（小規模入力の疎通確認）。
実ジョブのComfyUI historyでも、Euler 8 steps、VSA keep 10%、shift 12/3、Kitchen attention、seedを照合した。
別モデル・GPU・精度・attentionへの切り替えはしていない。

## 費用と停止

当初の合計上限6 CUを維持。旧側を再生成せず、失敗分を含む全5割り当てを集計した。

- 開始残高969.29 CU、最終確認時残高964.85 CU。表示差 **4.44 CU**。
- 残高の反映遅延と区別し、各割り当ての料金率×開始から解除後確認までの時間と残高差の大きい方を合計した概算は **5.09 CU**。課金確定額とは呼ばない。
- 全VMの解除、割り当て一覧が空、料金レート0 CU/h、孤立VMなし、監視プロセス終了を確認済み。
- 生成は完了し、追加の有料実行は行わない。

## 取得制限への対策（ローカルのみ検証）

今回の実行後、FastH3の取得に限って次を追加した。**429解消・実機生成成功は未確認。**

- ファイル取得は同時2本まで。Xet high-performanceを無効にし、range GETと固定download concurrencyに4を要求する。
- 実際に観測したXet `RuntimeError` の `429 Too Many Requests` のみ、同じ固定版のファイルを再試行する。
  待機は30・60・120秒、最大4回。認証エラー・404・その他エラーは追加再試行しない。
- 取得元、モデル、精度、sampler、request ID、旧経路は変更しない。自動的なVM再作成も行わない。

並列数の低下は制限を避けるための緩和策であり、高並列が今回の429の根本原因だったとは確認していない。
設定の意味は[公式環境変数資料](https://huggingface.co/docs/huggingface_hub/package_reference/environment_variables)と
[Xetの公式設定資料](https://huggingface.co/docs/hub/xet/using-xet-storage)を参照。
